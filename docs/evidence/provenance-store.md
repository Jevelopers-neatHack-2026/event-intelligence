# Internal evidence and provenance store

`src/evidence/store.mjs` is an internal persistence core for source evidence and extracted fact provenance. `src/verification/provenance/index.mjs` exposes a narrow in-process adapter over the fact operations. These files do not define a public package contract, canonical request/package serialization, authenticated route, or complete issue-10 integration. Those pieces remain dependent on the shared contracts and application composition root.

## Persistence and concurrency

The store creates one `evidence.sqlite` database under a private directory named by a SHA-256 tenant scope. SQLite stores the sanitized evidence/fact manifest and encrypted bundle rows together. Every store operation uses `BEGIN IMMEDIATE`; new encrypted bundles, metadata changes, and expiry deletes commit or roll back in one transaction. When a transactional store operation fails, its transaction rolls back first; a separate transaction then commits only the expiry sweep before the original error is returned. This preserves cleanup without committing a failed write. SQLite owns cross-process locking and releases an interrupted writer's transaction when the process exits. A per-tenant in-process promise queue prevents synchronous SQLite busy-waits from blocking an earlier async operation in the same process. Lock timeout failures surface as `EVIDENCE_BUSY`; there is no age-based stale-lock takeover.

Each lock operation has one original monotonic `lockTimeoutMs` deadline, starting before its tenant queue, filesystem/SQLite preparation and retries. Boundary checks read that clock as well as observing cancellation; delayed timer delivery cannot admit a new transaction after a slow final authorization callback. The same deadline is checked before transaction work and commit. A detected expired window rolls back staged changes and returns `EVIDENCE_BUSY`. An external cancellation already observed by the context retains `EVIDENCE_CANCELLED`. The budget does not include earlier key/encryption preparation and cannot preempt synchronous host callbacks or a native SQLite call. A completed commit remains committed if a later Promise continuation is delayed; this is not an end-to-end response latency guarantee.

The database uses rollback-journal mode, `synchronous=FULL`, `secure_delete=ON`, and private file permissions. The store sets tenant directories to mode `0700`, sets the database file to `0600`, and rejects an existing database path that is a symbolic link or non-regular file. Configure `directory` from trusted server-side composition. The implementation assumes the parent storage path and its filesystem administrators are trusted; it does not defend against a same-user attacker racing filesystem path replacement or an administrator directly editing the database. Use a local filesystem that supports SQLite locking and durability; no network-filesystem coordination guarantee is made.

The runtime uses the built-in `node:sqlite` `DatabaseSync` API and adds no npm dependency or native addon. This implementation was exercised with Node `v22.23.3`. In that release the module is available without `--experimental-sqlite`, but Node marks it Stability 1.1, Active development; the `DatabaseSync` busy-timeout option is available from Node `v22.16.0`. Host support outside the tested runtime is not asserted. See the [Node.js v22.23.3 SQLite documentation](https://nodejs.org/download/release/v22.23.3/docs/api/sqlite.html).

## Tenant, privacy, and retention boundary

The application injects `resolveTenant`, `resolveKey`, `resolveRetention`, and the private-read authorization hooks. The store derives tenant identity from `resolveTenant` and accepts only opaque, process-local tenant/evidence/position/fact handles afterward; public caller-supplied tenant fields are not part of its inputs. Returned handles and metadata are frozen. The retention capability is opaque and must bind to the existing privacy decision at the composition root. The store caps expiry by the injected decision and its configured maximum; facts cannot outlive their supporting evidence.

The complete source is hashed transiently and is not persisted as plaintext. Only caller-selected text ranges or JSON pointers that exactly match the source are persisted, inside AES-256-GCM encrypted bundles. Fact raw and normalized values are encrypted as well. A fresh 32-byte key is resolved from the injected key service for each payload/fact operation; the store does not contain a production key. The authenticated-encryption associated data binds the tenant hash, bundle kind, and immutable record ID. Source URLs and redirect chains are inside encrypted evidence bundles; source identity indexes use a keyed HMAC.

Private result operations require both an asynchronous pre-decrypt `authorizePrivateAccess` callback and the synchronous `authorizePrivateAccessCurrent` final hook. The latter is mandatory in `EvidenceStoreOptions`; missing, throwing, non-Boolean, or Promise results fail closed. A genuine native rejected Promise is given a rejection observer without awaiting or assimilating arbitrary thenables. The store passes the final hook the tenant derived from an opaque scope, the current host request, the exact action, and selected evidence/fact IDs. It must re-derive current host identity and ACL from trusted application state; caller tenant fields and the older precheck are not a fallback. The callback runs with no SQLite transaction or tenant queue held.

`materializeSelected(scope, { evidence, facts }, request, signal)` is the bounded all-or-error boundary for consumers that need a consistent set. It accepts at most eight direct evidence handles, 128 fact handles, and `min(maxPositionCount, 128)` total evidence positions; fact supports add their evidence automatically within the same eight-source bound. In addition to record counts, it caps selected sealed BLOB copies at 8 MiB total (4 MiB per evidence bundle and 512 KiB per fact), decrypted plaintext at 8 MiB total (4 MiB per evidence bundle and 256 KiB per fact, with 2 MiB total fact plaintext), copied fact metadata at 512 KiB, provenance and locator metadata at 512 KiB, and decoded position content at 1 MiB total. Per position, decoded content is limited to `min(maxPositionBytes, 64 KiB)`; per evidence record, total position content is limited to `min(maxStoredPayloadBytes, 512 KiB)`. These effective caps preserve lower configured store limits and apply the fixed batch ceiling when configuration is higher. Length-only SQLite queries check aggregate sealed BLOB sizes before the implementation copies any BLOB. Ciphertext length bounds are checked before key resolution and decryption; position and provenance byte counts are checked while materializing, before each decoded-content copy or public result is released. Fact support references are bounded to 4,096 across manifest metadata and decrypted facts.

The all-or-error path follows only the explicitly selected fact IDs and their stored supporting evidence IDs; it does not copy unrelated sealed rows or source-position payloads from the tenant. The current on-disk index remains one tenant manifest JSON document, which is parsed and validated as a whole before selected record lookup and has a hard 16 MiB size limit. Only after the final current-authorization hook returns does final verification open a short synchronous read transaction: it checks the manifest length before copying that document, then checks the selected records in the same transaction. No await, host callback, or tenant queue/write transaction spans this final verification; the store clock and each selected expiry are checked before release. For evidence links, absent and `null` predecessors compare equivalently; a prior non-null link may be cleared only when that exact predecessor is now an expired tombstone. Hashes, positions, source descriptors, keys, policy metadata, and retention deadlines still require equality. `listFacts` accepts an absent manifest only when no manifest row existed at snapshot time and there are no sealed bundles; a persisted manifest or selected record that disappears fails closed. That bounded tenant-wide manifest parse is still a known scaling cost. `listFacts` is a separate whole-tenant API with its existing 1,000-fact cap and the same sealed, decrypted-fact, fact-metadata, support-reference, and provenance byte budgets. It counts each decrypted support occurrence, including duplicates and conflict candidates, and checks those bytes before creating public support handles; it does not inherit the selected API's eight-source or 128-fact caps.

After final authorization, the selected path performs only synchronous persisted-state, per-record store-clock/expiry, and cancellation checks before returning deeply frozen selected values. It never returns source or position bytes. Its source descriptor, original retrieval timestamp, full-source hash, metadata, and position digests come from the stored encrypted record, so idempotent same-byte replay cannot make old evidence look newly retrieved or replace its stored URL/content type. The full-source hash and selected-position digest remain separate.

The existing private read methods use the same current final gate. `readFact`, `listFacts`, and `listEvidencePositions` decrypt from copied ciphertext after closing the database transaction, then recheck persisted state and retention before publication. A tenant with no persisted manifest is a valid empty state for `listFacts`; a manifest that was present at snapshot time cannot disappear during the read. `listFacts` fails the complete snapshot with `EVIDENCE_EXPIRED` when any fact expires; it never publishes a partial list. `withPrivatePayload` supplies bytes only to the trusted synchronous consumer and rechecks authorization, persisted state, and expiry after that callback. Native Promise and custom thenable consumer results are denied; synchronous results are copied into frozen JSON-compatible data (or `undefined`) so the async API cannot adopt a consumer thenable. Returned arrays retain normal readonly iteration and array methods; a copied top-level array has a non-enumerable inert own `then` value so inherited thenables cannot be adopted. There is no raw-payload return method.

Expiry deletes encrypted evidence/fact bundle rows and strips content hashes, timestamps, policy details, source HMAC linkage, and support links from tombstones in a committed cleanup transaction. The same tenant transaction sweeps expired pending and complete private-retrieval receipts, nulling their key ID, payload digest, plaintext byte count, and encrypted envelope while retaining only the tenant-bound opaque receipt key, schema version, expired state, expiry time, and update time needed for sanitized deduplication. This receipt sweep is bounded by the existing 4,096-row and 32 MiB per-tenant receipt limits. It runs through the ordinary expiry path as well as `purgeExpired`; cancellation or transaction failure rolls the cleanup back and cannot commit later after a cancelled SQLite wait. When an operation fails because a selected record expired, that sweep commits separately after the failed read/write transaction has rolled back. An evidence tombstone retains only its opaque ID and expired state; expired facts retain only their opaque ID and expired state. New writes and idempotent ingestion recheck retention after asynchronous key work so an expired record is never reported as available. The store does not change or silently extend the upstream privacy retention decision.

`purgeExpired(scope, signal?)` returns its historical count of expired evidence and fact records; it does not include receipt tombstones in that number. `integritySnapshot` reports `encryptedPayloadRecords` for evidence/fact bundle rows and separately reports `encryptedPrivateReceiptRecords` for every non-null receipt envelope in that tenant database. A zero in the former field alone does not mean no encrypted receipt remains; after expiry cleanup both counts are zero when no live encrypted records remain.

## PDF-derived evidence

`ingestDerivedPdfEvidence` accepts only a copied `Uint8Array` containing the exact fetched PDF bytes. It rejects strings so UTF-8 or another conversion cannot silently change which bytes the source hash identifies. The store invokes the pinned `readTextPdf` implementation itself; caller-supplied text, geometry, hashes, decoder configuration, loaders, or observations are not accepted. The original full-byte SHA-256 remains the source `contentHash` and is distinct from the digest over derived pages, boxes, text hashes, and effective decoder limits. The original PDF bytes are hashed transiently and never persisted.

The reader runs outside store transactions and the tenant write queue. A successful observation persists the complete page list, including pages with no embedded text, plus extracted text under explicit `pdf-text-box` locators with approximate page geometry. These locators are derived observations, not byte ranges or JSON pointers into the original PDF. The result is always marked `incomplete-text-only` and `requiresInspection: true`; it does not establish that text extraction found every event detail or that a page is visually legible. A valid PDF with no embedded text returns the non-persisted `no-text` result. Decoder rejection, cancellation, invalid geometry, a breached cap, or any incomplete record returns without an evidence handle or partial saved pages.

The default reader input limit is bounded by `min(maxSourceBytes, 5 MiB)`. Effective text and output limits may be lowered per call and cannot exceed the fixed reader maxima (including the reader's 2 MiB output limit) or the derived-store ceilings. The persisted positions remain bounded by `min(maxPositionCount, 128)` total boxes, `min(maxPositionBytes, 64 KiB)` per box, and `min(maxStoredPayloadBytes, 512 KiB)` aggregate text bytes. Serialized derived provenance is limited to 512 KiB, each evidence bundle to 4 MiB, and the complete tenant manifest to 16 MiB. A cap breach is all-or-error; raising the trusted store configuration cannot raise the derived source, reader-output, position, provenance, or bundle ceilings. These are input and persistence ceilings, not a process-memory, latency, or host entitlement certification.

Derived records are encrypted with the existing AES-GCM evidence-bundle path and the existing authenticated-data binding of tenant hash, kind, and immutable record ID. The schema-version-2 bundle contains the original source descriptor and exact `retrievedAt`, full source hash, page metadata, text positions, and derivation digest. Metadata-only selected materialization returns stored descriptors and hashes but no extracted text. Text is available only through the existing final-authorized private consumer path, which remains synchronous and trusted. The app composition root must supply current tenant and ACL authorization for the exact operation and evidence IDs; there is no legacy authorization fallback or independently usable release authority in this feature.

The privacy retention decision is resolved before decoding starts. The store rechecks cancellation and that original deadline after decode and asynchronous key/authorization preparation. After the final current-authorization hook returns, a short synchronous SQLite transaction rechecks the persisted manifest snapshot and store clock after acquiring `BEGIN IMMEDIATE`, then again immediately before commit. No authorization, key, consumer callback, or `await` is run while that write transaction is held. The trusted synchronous `now` function is invoked for expiry checks and must be pure and non-reentrant. The same post-lock expiry checks apply to idempotent replay. If the deadline expires during a busy wait or write, SQLite rolls back the new record; a separate expiry sweep may commit afterward, and no handle is released. A replay returns the old immutable evidence ID, source URL/content type, and original retrieval time; a changed derivation configuration produces a new immutable version rather than rewriting that provenance.

Derived family HMACs use a domain separate from raw evidence identities. A derived version is idempotent only when the source family, exact original PDF hash, and derivation digest match. The `duplicateGroupId` remains an exact original-byte duplicate marker and is not evidence of independent support. Derived positions are rejected by `appendFact`, and the unchanged source-identity composer continues to reject `pdf-text-box` locators as raw source positions. A future fact-extraction adapter must define its own authorized interpretation boundary.

Raw schema-version-1 bundles remain encrypted and are read without decryption/re-encryption during upgrade. The first derived commit atomically changes only that tenant's manifest to version 2 together with the new sealed bundle. A previous v1-only binary rejects a v2 manifest and must not be allowed to write the tenant after migration; deployments need a coordinated binary cutover. The store does not migrate every tenant or rewrite old bundles, and unknown schema versions fail closed.

The actual reader-to-SQLite integration is registered separately as `make verify CASE=pdf-derived-evidence MODE=linux-integration` and runs on Linux with Node 22.23.3. It uses local synthetic documents, trusted test keys, and test authorization/retention adapters; it makes no provider requests. The route fails on unsupported platforms instead of counting the reader's isolation-unavailable response as a pass. The ordinary `evidence-facts` mock route is unchanged. The PDF-derived route covers actual decode, encrypted close/reopen and authorized text readback, v1-to-v2 migration, immutable replay/version behavior, no-text/rejection, retention and cancellation, raw-composer rejection, and competing SQLite processes. Passing it validates this scoped persistence adapter only, not the complete issue-10 or issue-12 requirements, production authorization, server compatibility, or system release readiness.

## Provenance semantics

Facts distinguish `sourced`, `inferred`, `customer_supplied`, `missing`, and `conflicting` states, and preserve raw and normalized values separately. A sourced/inferred support must refer to an authorized evidence handle, an issued position handle, the matching full-source hash, and the saved position hash. Date-only precision stays date-only; the store does not infer a time or timezone. Conflicts preserve each candidate and its own supports.

`duplicateGroupId` groups records with exactly identical source bytes within a tenant. It is a duplicate marker, not evidence that other sources are independent. Every fact support reports `independence: 'unknown'`; the API intentionally exposes no independent-support count because different hashes, publishers, hostnames, and brand names do not establish independent origin. Authority is not inferred from branding. Attribution-aware independence can be added only when a trusted provenance signal exists.

## Validation boundary

Run the raw evidence and fact suite with `make verify CASE=evidence-facts MODE=mock` on Node 22.23.3. The older `CASE=evidence` selector remains a compatibility alias and reports the canonical `evidence-facts` case. The dedicated `.github/workflows/selected-evidence.yml` job runs those store, extraction, and identity regression suites plus strict consumer types. The derived-PDF workflow uses the separate Linux-only route described above. Tests use synthetic tenant keys, requests, and retention capabilities. They cover process restart, same-process and cross-process competing writes, SIGKILL rollback of staged ciphertext and metadata, busy timeout with a live writer, symlink rejection, hash/position/scope validation, idempotency and changed-byte versions, conservative syndication grouping, expiry cleanup after failed operations, cleanup isolation from rolled-back writes, delayed-key principal/ACL changes, aggregate fact/source expiry, final-hook reentrancy, changed state during authorization, tombstone metadata serialization, exact and over-limit sealed/fact/provenance/position byte budgets, and rejection before key resolution where encrypted lengths are known. This is persistence and fact-validation core coverage, not proof that the broader event-intelligence package or authentication routes are complete.

The selected boundary is an internal store capability, not an accepted canonical ResearchRequest/EventIntelligencePackage serialization contract or an authenticated route. Its final authorization hook still requires the trusted application composition root to provide a current tenant/ACL decision; unit tests use synthetic adapters and do not establish production authorization, server compatibility, external-source authority, or whole-issue closure. These byte budgets are code-level ceilings tested on Node 22.23.3, not a server memory or latency certification. Deployment LVE/RAM entitlements are unknown, and no callback duration is forced or guaranteed.
