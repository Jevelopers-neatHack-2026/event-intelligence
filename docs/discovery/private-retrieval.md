# Private retrieval lifecycle

`runPrivateRetrieval` is an internal composition of the durable discovery frontier, the existing `SafeFetcher`, deterministic extraction, the encrypted evidence/fact store, and the existing source-identity composer. It returns a private, bounded draft for an authorized host to inspect. It does not add a public `ResearchRequest` or event-package schema, authenticate a product request, establish a trusted source or rights decision, invoke a provider, measure external egress, inspect or promote image rights, or close the related project issues. Customer-supplied material without a real intake and storage path remains unsupported here; it is not assigned a synthetic network URL.

## Transport and restart accounting

Each actual initial, retry, or redirect hop is admitted in one SQLite transaction before its transport-dispatch intent. Admission reserves the full 20 MiB decoded ceiling for that hop against a 100 MiB run budget. The separate states `reserved`, `dispatch_intent`, `response_received`, `body_complete`, `known_zero`, and `unknown` describe different durable facts. An existing attempt key is only historical deduplication and never authorizes a second dispatch. A crash after dispatch intent, response receipt, or partial decoding keeps the full reservation as unknown; only positive evidence that decoding never began may release it as known zero. A completed body settles to its exact byte length only after EOF and body construction. The remaining reservation is never reset on restart.

The frontier schema is v3. V1 persisted attempt admissions but no transport or decoded-byte evidence, so a v1 run with any admitted attempt migrates to a full-run unknown reservation. It cannot spend new transport capacity or seal a draft; a v1 run with no admitted attempt retains its unused budget. V2 already has the per-hop transport ledger, and both v1 and v2 databases migrate transactionally to v3. Tests execute the pinned v1 producer from `d91e08d666abc243ae456a7f9f1bc9c745ca4f8d` and pinned v2 producer from `d1731173b5ccb6f5212d6e83c71ebd1a8d4ff66f`, verify their source hashes, reopen the same databases, and preserve their historical snapshots and admission behavior.

## Opt-in controlled SVG acquisition

Asset acquisition is off unless the host supplies a non-null versioned `assetAcquisitionPolicyFor` result and an `assetAcquisitionReleaseAuthorityFor` issuer. The canonical policy, its exact origins, and the one-shot release protocol version are included in the immutable frontier run configuration; changing the policy or widening a default-off run is rejected. With `maxDepth: 0`, no asset URL is requested. Otherwise the runner admits an asset URL as an ordinary child in the existing frontier and spends the same admission, decoded-byte, deadline, suggestion, and lease budgets. It never starts an independent asset run or uses a second `SafeFetcher` budget.

The issuer should call `createPrivateAssetReleaseAuthority({ tenantId, runId, policy, expiresAtMonotonic })` using the authenticated tenant, the supplied run and normalized policy, and the supplied monotonic deadline. It returns an opaque controller held by the host authorization layer. The host must call `controller.revoke(reason)` synchronously when tenant, release, asset, or policy authority changes. The capability is bound to the tenant, exact run ID, normalized policy digest, deadline, and the sorted candidate set selected by the store. A copied `revoke` method or hand-built controller does not reproduce the opaque capability. The controller can be consumed once; expired, revoked, replayed, or differently scoped capabilities fail closed. Revocation before projection returns `before_release` and prevents the draft. Revocation after a successful synchronous projection returns `after_release` and does not retroactively change that released result.

An asset child is recognized only from the exact parent completion receipt's encrypted asset-suggestion binding and a fresh reopen of the current encrypted asset-source excerpt. The binding covers the source candidate ID and version, page/source content hash and derivation, lexical excerpt hash, locator, field/value, and canonical fetch URL. A copied reference, changed candidate, stale source, ambiguous candidate, seed, or ordinary link cannot be upgraded to asset purpose. The binding is carried by the encrypted child receipt and rechecked before the one-hop request. Its completion writes separately encrypted `fetched-source` and `transformed` evidence. Both records are reopened under current tenant authorization and independently checked before the runner emits a blocked candidate-bound local plan.

The SVG mode accepts one `image/svg+xml` response up to 128 KiB, with no redirect request or subresource fetching, and independently parses and sanitizes the actual bytes under the existing safe-asset inspector. Host and selected-materialization byte/position ceilings can lower these limits. The raw response and transformed bytes remain distinct evidence roles even when a canonical SVG transforms idempotently to identical bytes. Stored evidence expires no later than the current source excerpt. The local `Q-EI-BRAND-ROLE:v1` plan remains `blocked` and `not_dispatched`; observer metadata is absent or caller asserted, and the flow makes no accepted external asset-version, role, ownership, rights, permission, issuer, or creative-promotion claim.

The package export map intentionally excludes `security/internal/fetch-lifecycle`. The private retrieval composition and evidence store are trusted internal callers of that lifecycle witness; this is a package-module boundary, not an adversarial same-process sandbox. Supported package consumers cannot import the witness factory through package subpaths, and the store rejects copied documents with an ordinary caller-created witness. Direct source imports into internal modules are outside the supported package API.

V3 claims store a binding version and the highest observation sequence present when the claim is first committed. A receipt replay reconstructs candidate depth, seed status, supplied URL, and source references from that exact tenant/run observation prefix. Later duplicate, canonical, backlink, or cycle observations remain visible in current frontier progress but cannot rewrite the candidate already bound to a receipt. Retrying the same claim key or reopening the database preserves its original cutoff. Migrated v1/v2 claims are explicitly marked as legacy with no cutoff; the reader does not infer one retroactively, and the runner retains the strict legacy-current-candidate compatibility path for those old claims. A new v3 claim with a missing, mixed, out-of-range, gapped, malformed, or otherwise inconsistent prefix fails closed without receipt replay or redispatch.

Replay also bounds each outgoing observation by the authenticated candidate depth captured at claim time. An observation must be at least one level deeper than the candidate's current best depth and at most one level deeper than its authenticated claim depth. This permits a later verified link to lower the candidate's best depth before its receipt is replayed, while preventing coordinated edits to child depth and observation depth from exceeding the authenticated claim. The final projection snapshot receives the same check.

The runner also carries one monotonic deadline from entry through scope creation, network work, callbacks, final lookup, sealing, and selected evidence materialization. It races awaited host/store work against cancellation and deadline, closes active requests, rejects late callback results, and persists a deadline even after the last admission changed the frontier's primary stop reason to `attempt_limit`. A late `createRun` completion receives the already-expired durable stop and cannot dispatch. After an abort, cleanup shares a 750 ms scheduled-await budget: stop persistence is signalled to abort after at most 500 ms or the shared budget's remaining time, whichever is shorter, while each transport or unresolved-lease cleanup write receives at most 250 ms and only the budget's remaining time. If the envelope is already exhausted, the stop callback receives an already-aborted signal and no new stop timer is started. The shared envelope ends 750 ms after the earlier of the observed stop and the original monotonic run deadline, so delayed deadline delivery cannot grant a new cleanup window. Once stop persistence has started, the first unresolved-lease write is capped at 100 ms to reserve time for the stop attempt and one uncertainty retry. Deadline recovery waits for the stop write to settle within that budget before its single uncertainty retry. These timers cannot interrupt synchronous store work or prevent event-loop scheduling delay. The maintained integration fixture records the original cancellation-to-return interval and uses an independent native timer, registered before cancellation for the original 750 ms boundary, to observe when that boundary can be serviced. It requires return within 100 ms of the latest of that original boundary, the sibling abort listener returning, and the independent timer being serviced. A native blocked-service control preserves its measured violation of the old absolute 850 ms assertion while checking prompt cleanup after service resumes; this is a scheduled-await invariant, not an unconditional physical return-time guarantee. A separate controlled overrun case verifies that synchronous work consuming the entire envelope cannot grant another scheduled wait or an active stop-persistence signal after the event loop resumes. If cleanup cannot settle in time, the run remains incomplete; possible admissions retain their existing reservation and spent-byte accounting, and restart never redispatches an uncertain admission. Sealing prevents queued candidates from being claimed or admitted later while retaining their metadata in an incomplete draft.

The final controlled-asset preflight is raced against that original signal and deadline. If either wins, the host controller is revoked synchronously; a late successful opaque check is discarded once, and a late rejection is observed without changing the incomplete result. A never-settling preflight cannot hold the run open. This callback boundary accepts ordinary native promises from the current or another realm only when descriptor checks confirm the intrinsic Promise constructor/species path and there is no own `constructor` property. It never reads a returned value's `then` property or adopts a thenable. A host adapter returning an exotic or subclass Promise must observe its rejection before returning; that value is denied without invoking its constructor or species accessors.

The deferred stop-persistence callback also rechecks its absolute signal deadline immediately before entering the host's `stopRun` method. That deadline is the earlier of its original 500 ms allowance and the shared cleanup envelope. A synchronous sibling cancellation listener can delay the callback's microtask until an abort timer is overdue; in that case the host receives an already-aborted signal on entry. The check covers both an expired stop allowance with time left in the shared envelope and an entirely exhausted envelope. When the shared wait for stop persistence expires, it explicitly cancels every pending stop signal and clears its timer before returning, including when the wait's timer runs before a stop timer due at the same boundary. Valid earlier stop attempts keep their existing allowance. These checks do not interrupt synchronous work, renew either deadline, or imply that a canceled persistence operation succeeded.

## Source refusal reasons

The source composer preserves bounded extractor refusals before any source or fact is persisted. The private runner records the corresponding sanitized limitation in the existing encrypted completion receipt, so reopening the same run retains the reason without another request. These are observations of the supplied response; they do not authorize rendering, access bypass, a provider fallback, or a successful package.

| Extractor refusal | Private limitation | Supported next input |
| --- | --- | --- |
| `JS_REQUIRED` | `dynamic_rendering_required` | An accessible static public source containing the requested facts |
| `ACCESS_RESTRICTED` | `source_access_restricted` | An accessible public source; no login or challenge bypass is attempted |
| `UNSUPPORTED_MEDIA` | `unsupported_media` | A supported text representation, or the separately supported text-PDF path |
| `UNSUPPORTED_ENCODING`, `MALFORMED_ENCODING` | `malformed_or_unsupported_encoding` | A supported UTF-8 source with consistent declarations |

Cancellation and resource termination keep precedence over these source-level observations. Unclassified unusable extraction retains `source_incomplete_or_access_restricted`. Existing historical receipts keep their recorded generic limitation; reopening them does not infer a more specific past outcome. Malformed text rejected by `SafeFetcher` before extraction remains `unsupported_media`. No factual draft is released for a run containing only refused sources.

## Private completion receipts

The evidence store adds a separate `private-retrieval-receipts` extension schema (version 1); it does not change the evidence manifest's historical v1/v2/v3 payload profiles. A bounded AES-GCM receipt uses the existing `payload` key-resolution purpose and a distinct `private-retrieval-receipt` associated-data kind. It binds the tenant, run configuration, exact frontier candidate and claim, completion outcome, selected evidence/fact IDs and versions, content hashes, source positions, and source-to-identity candidates. Receipt plaintext is capped at 512 KiB per row and the tenant table is capped at 4,096 rows and 32 MiB of sealed envelopes. Its plaintext SQLite columns contain only bounded tenant/run lookup hashes, state, key id, payload digest/length, expiry, and the encrypted envelope; fact values and excerpts are not placed in frontier metadata.

A pending receipt is written before transport admission. New v3-claim receipts also bind the exact supplied URL from the immutable observation prefix inside the encrypted candidate record; the evidence store validates its URL syntax, canonical destination, and sensitive query/fragment policy before sealing. Historical v1/v2 receipt bodies omit this optional field and are read only through their explicit legacy claim path; they are not rewritten or assigned a retroactive URL cutoff. A complete receipt is committed only after the selected encrypted evidence and facts have been materialized and current authorization, expiry, retention, and manifest-version checks pass. The frontier completion remains a separate SQLite transaction: if evidence commits but the complete receipt does not, recovery reports explicit uncertainty and never redispatches the old lease; if the receipt completes first, recovery may finish that exact claim from the receipt without another request. A pending, missing, expired, mismatched, revoked, or otherwise unavailable receipt cannot produce a draft. Every complete replay reopens and reauthorizes each referenced evidence and fact record, then rebuilds cross-source identity from the encrypted candidates. A receipt is a recovery index, not a cached disclosure or authority grant.

Receipt expiry is also swept tenant-wide on ordinary evidence-store expiry operations and by `purgeExpired`, without requiring the exact run/config/candidate key to be read. The sweep clears expired pending and complete ciphertext, key IDs, payload digests, and byte counts, and retains only the sanitized expired deduplication row. It is bounded by the existing 4,096-row and 32 MiB per-tenant receipt limits and shares the enclosing SQLite transaction, so cancellation and rollback cannot leave a late cleanup commit. `purgeExpired` keeps its evidence/fact count; `integritySnapshot.encryptedPrivateReceiptRecords` reports receipt envelopes separately from `encryptedPayloadRecords`.

Each private completion reads `maxSuggestionsPerCompletion` from the persisted frontier run. It orders eligible suggestions by URL and exact source-reference fields before splitting them, sends only the bounded prefix to the frontier, and records the omitted valid URLs with their exact source references in the encrypted receipt. The draft exposes those records as `omittedLinkCandidates` with reason `completion_suggestion_limit`; they are not queued candidates and carry no authority decision. `truncatedCount` and `omittedSuggestions` are replayed unchanged, and the frontier stores a `fanout_limit` stop when that count is positive. The source composer’s separate `linkCandidatesOmitted` count is stored as `sourceLinkCandidatesOmittedCount`; it covers links rejected or omitted earlier by parser/policy bounds, so their unsafe or unbound raw values are not retained. A replayed historical v1 receipt that carries the existing parser/policy-omission limitation has an unknown exact count: progress reports `sourceLinkCandidateOmittedCount: null`, adds one proven omission for the run-level marker plus exact counts from new receipts in `sourceLinkCandidateOmittedCountLowerBound`, and reports `sourceLinkCandidateOmittedCountComplete: false`. A v1 reader’s compatibility default of zero is never promoted to an exact count for an individual receipt. The baseline writer deduplicated limitations in a run-level set and emitted this marker only when that run had a positive parser/policy omission; only after all completed receipts for a recovered baseline run have been authenticated and the preserved marker set is known to be empty does its absence establish a run-level zero. New receipts persist exact zero or positive counts.

These fields are optional additions inside the existing encrypted receipt body and do not change the receipt table or extension schema version. Historical v1 completion bodies are decoded with zero omission defaults while retaining their original property shape for hash-based idempotency. If an old leased receipt contains more suggestions than its persisted frontier cap, recovery uses the same deterministic split without redispatch. For an already-completed historical receipt, recovery checks the exact stored frontier payload hash and observations before reporting a recovered split; if the prior partition cannot be proven, it returns an incomplete result with `legacy_receipt_fanout_recovery_unverified` instead of guessing or rewriting the old receipt.

## Decoded stream limit

The private path accepts at most 20 MiB minus 64 KiB of decoded text per response and 10 MiB minus 64 KiB of decoded media. Encoded response bytes remain subject to the existing 10 MiB wire ceiling. The private gzip path sets the native zlib output chunk and each participating stream high-water mark to 4 KiB. A local output transform increments its decoded production counter before forwarding each chunk, so the byte that crosses the accepted limit is rejected at that transform; completed, accepted body bytes are counted again by the iterator that retains them. The durable per-hop reservation remains full until successful EOF settlement, covering crashes between production and the ledger transaction.

The 64 KiB headroom is for additional decoded production around the guard, not for all live body memory. For the pinned Node 22.23.3 stream/zlib sources used by CI, a conservative accounting envelope is 44 KiB: one 4 KiB native zlib output buffer; one 4 KiB high-water mark plus one 4 KiB push for Gunzip's readable queue; the same allowance for the output transform's writable queue; the corresponding output readable queue; an async-iterator aggregate no larger than that readable queue; and the `Buffer.from` accumulator copy of that returned chunk. This coarse sum intentionally counts overlapping and already-counter-accounted chunks again. `Readable` high-water marks can be crossed by one current push, so each queue includes a full extra chunk. The transform pipeline pauses its source when a destination write returns false; `Transform` withholds its callback when the readable side reaches the high-water mark; zlib's callback defers another native write after a full readable push. These pinned source behaviors bound the additional output-stage production around the guard to the configured queue plus one 4 KiB chunk per stage. The output guard increments before forwarding a chunk, and the one chunk that crosses the accepted threshold is rejected before forwarding. Even if the entire conservative 44 KiB allowance were additional to the guard's counter, it is below the 64 KiB headroom by 20 KiB. `Readable.fromList` can aggregate queued chunks, so the iterator return is included.

The accumulator retains copies of accepted chunks and `Buffer.concat` then creates the SafeFetcher body, so those two full representations can coexist temporarily and may approach twice the accepted body size. That duplication carries the same accepted source bytes; it is not extra decompressor output and is not bounded by the 44 KiB allowance. The 44 KiB calculation does not claim to cap total live decoded memory, V8 heap, native allocator state, socket buffers, kernel memory, or operating-system memory. The HTTP/TLS input buffers contain encoded wire data and are separately subject to the 10 MiB wire guard. JavaScript also cannot guarantee erasure of copies already held by the runtime or a trusted callback.

Identity bodies do not expand. Every chunk must pass the cumulative 10 MiB `wireGuard` before it can reach the output guard, so identity bytes entering the accepted parser path stay below the full 20 MiB hop reservation even if the smaller text/media accepted limit rejects the response. For gzip, encoded input is separately stopped by the same wire guard and decoded output passes the 4 KiB output guard before retention. Node's `IncomingMessage` uses the socket readable high-water mark; `parserOnBody` pushes the current parser chunk and pauses the socket when that push applies backpressure. This accounts for the source/read-ahead stage: those pending bytes are still encoded input for gzip, and identity has no expansion and cannot pass the cumulative wire guard as accepted output. The high-water mark and one current push are not asserted as a whole-process hard memory quota. This accounting does not certify V8 heap, native allocator state, socket buffers, kernel memory, or operating-system memory. JavaScript also cannot guarantee erasure of copies already held by the runtime or a trusted callback. Runner-owned body, chunk, extraction, and draft-position buffers are wiped or dropped on the cleanup paths where the implementation owns them.

The source files and hashes for Node 22.23.3's readable, writable, transform, pipeline, HTTP, net/TLS, and zlib internals are recorded in the execution evidence manifest. Local stress tests exercise an over-limit gzip expansion, truncated gzip after decoded output, identity wire-limit interruption, cancellation during a slow response, and crash/restart reservation retention. Linux CI executes the actual PDF path; a Darwin skip is recorded as a skip, not a pass.

## Release checks

Before the draft is released, the runner seals against new frontier work and asks the evidence store to materialize the complete selected evidence/fact set under its current ACL, key, expiry, retention, and cancellation checks. The runner compares that materialized set with the composer output after all awaited work. For an opted-in run, it reopens active fetched/transformed roles and performs the last awaited current-policy check, then asks the store for an opaque single-use release check. The synchronous `finalizeControlledAssetRelease` call verifies the exact controller and candidate set, rederives current store authorization, rechecks persisted selected evidence, fact supports, role records, and retention deadlines, and invokes the bounded draft projection in the same call stack. No awaited or external callback follows that projection. Thus queued callbacks from earlier async work run before the release call; synchronous reentrant revocation is detected before projection; queued revocation after projection is classified as after-release. This is a serialized in-process composition contract: the host must revoke its controller as part of each authority change, and the controller does not sandbox independently mutated state in another process. The zero-asset opt-in path uses the same final fact/source check with an empty asset-group set, so removing every stale plan cannot skip final selected-evidence validation. Default-off runs retain the historical `EvidenceStore` input type and do not require the new methods or issuer. A seal that wins against cancellation does not bypass a later authorization, expiry, key, or retention denial. Diagnostics and durable progress contain bounded IDs, status, and stop codes, not extracted excerpts or fact values.

Sensitive seed and observed URLs are rejected before plaintext frontier metadata persistence; they are not stripped into a different fetched URL. Redirect targets pass the same URL and credential checks before per-hop admission. Source authority, usage, rights, and external provider states remain explicitly unknown or unevaluated in this private draft.
