# Source identity question preparation

`prepareIdentityQuestionFromComposition(composition, { candidateIds, languageByEvidenceId })` is an internal, offline adapter for an explicit pair of occurrence candidates returned by `composeSourceIdentity`. It projects only those candidates’ supported claims into the maintained `Q-EI-IDENTITY:v1` preparation API. The caller names exactly two distinct candidate IDs; the adapter does not select, merge, rank, or prefer candidates or claim values.

The adapter uses the occurrence candidate values emitted by the composer. For example, a JSON-LD value with surrounding whitespace has an exact raw token in the composer's private fact records and a normalized value in the supported occurrence claim. The question observation and its support reference carry the supported occurrence value, and the sidecar keeps that same value with the exact field, locator, evidence ID, and full-source hash. Before projection, the adapter checks the extraction source hash and status-mention collection of each source supporting the selected pair. It does not read source bytes or notice contents. Historical composition v1 does not inspect `composition.facts` or source URLs. Current v2 additionally checks the [retained attribution graph and its separate fact bindings](../discovery/source-corroboration.md) against the supplied facts, source metadata, extraction pointers and raw declaration tokens; these checks grant no authenticity or current authorization.

If a selected source has any visible status mention, preparation throws the private `SourceIdentityQuestionPreparationError` code `VISIBLE_STATUS_REVIEW_REQUIRED` and returns no plan or sidecar. This prevents stale structured `scheduled` claims from producing an eligible question that omits a visible cancellation or rescheduling notice. The adapter cannot safely assign document-level text to an occurrence, so ambiguous notices on pages with multiple editions and negated notices also require review; it does not change either candidate's status. The caller must keep the original composition and source evidence for review rather than discard the notice and retry with an empty collection. A notice in an unrelated source does not block the selected pair.

The selected extraction hash must match its evidence summary. Own data descriptors are required; missing or malformed extraction metadata, proxies, accessors, and sparse arrays fail closed without invoking caller code. The status collection is bounded at the composer's 32 mentions per source before entries are enumerated. A nonempty valid collection triggers review without inspecting or serializing its notice contents; an excessive length produces `RESOURCE_LIMIT_EXCEEDED`. These checks establish consistency within the supplied object, not authenticity or current authorization.

Every support must resolve to an evidence summary in the same supplied composition with a matching evidence ID and full-source hash. The selected pair’s maintained occurrence decision is recomputed and checked against its returned decision. A sidecar retains candidate claims, temporal precision, field-specific critical tags, duplicate group IDs, source timestamps, duplicate hashes, transitions, and unresolved transition diagnostics. Current composition output leaves cancellation and reschedule links empty and records those statuses as unresolved; preparation preserves that state without creating predecessor or successor relationships. Equal bytes remain duplicate evidence and are never counted as independent corroboration.

The maintained preparer’s whole-plan byte ceiling is tighter than one observation per field for a real two-candidate pair. To preserve all claims without exceeding that existing ceiling, the adapter groups text only for the same explicitly selected candidate, evidence ID, full-content hash, and caller language label. A group contains deterministic compact JSON for every normalized field, value, origin, temporal precision, and critical retention tag from that source identity. Different candidate or source identities always produce separate observations. Multiple support locators for the same claim and source remain separate in the sidecar, while repeated claim values from that same source appear once in its text group; no extra corroborating source is inferred. The immutable sidecar retains the exact per-field support values, locators, hashes, and duplicate-group IDs and maps them to each observation group. Group references hash the exact sanitized group contents. The composition ceiling of eight sources bounds this pair to at most 16 candidate/source groups; the maintained 32-observation cap remains enforced as a forward-compatible guard, though 32 groups cannot be reached with the current source and pair bounds.

Comparator provenance references have their own bound after grouping. The selected pair is capped at 128 supported claims, matching the composer’s total fact limit, and each claim accepts at most eight support references. The adapter therefore accepts up to 1,024 distinct references; it does not reuse the unrelated 32-observation limit. A regression starts from actual composer output, adds 33 valid supported claims across the two selected candidates, and verifies that all 33 references survive in the two grouped observations and sidecar.

The `sourceIdentityBinding` is an immutable local review sidecar. Its domain-separated digest binds the selected projection, grouped observation references and exact group contents, the plan’s source evidence hash, target binding and state hashes, question instance hash, and plan hash. The sidecar limit is 65,536 serialized UTF-8 bytes; the adapter preflights its sanitized JSON byte size before hashing or full serialization, and fails the whole operation when that limit or an upstream question-preparation limit is exceeded. It does not truncate claims or references. The maintained parser counts UTF-8 bytes from both each observation’s `text` and `claimText` fields. This adapter supplies the same grouped JSON text in both fields, so its `observationTextBytes` limit counts each group twice and matches the parser’s 10,000-byte aggregate cap. The maintained question limits also cap the plan at 32 observations, 4,096 UTF-8 bytes per observation text field, 16,384 bytes of state, and 32,768 bytes of plan.

The offline boundary suite reaches exactly 4,096 bytes for one observation, exactly 10,000 aggregate input text bytes, and exactly 65,536 sidecar bytes, then rejects each applicable first-over case without truncation. The existing synthetic projection/sidecar fixtures are explicitly historical v1; separate actual v2 composer fixtures with retained declarations exercise the exact observation and aggregate text limits including their new dependence context. A separate one-megabyte caller string is rejected at the length bound before Unicode, whitespace, or byte scans. The current 32-observation bound is guarded but unreachable under the eight-source/two-candidate projection ceiling.

Current composition v2 uses `ei-source-identity-question-binding-internal/v2` and a v2 domain for binding and grouped-observation digests. Its grouped JSON contains `{claims, corroboration}`. Historical v1 keeps the original claims array and v1 domains; a malformed v2 is refused without fallback. Dependence clusters preserve each selected candidate/source observation, its conflicts and all provenance. Their compact context states explicit unknown independence and unestablished origin; cluster membership never grants officialness or verified status. The private sidecar includes a stable source graph digest and the distinct per-result declaration-to-fact IDs, which are intentionally separate from the graph's replay-stable hashes. No canonical wire schema or provider API changes.

Language is absent from the source composition. A caller may supply one language label per evidence ID; the value is explicitly unverified metadata. Missing labels become `und`, and known non-English or multilingual labels use the question policy’s review behavior. The adapter does not infer language from claim text, URL, host, or source metadata.

The input object can be forged or stale. Its retained `retrievedAt` and `expiresAt` values are provenance only; the adapter does not authenticate the composition’s origin, establish tenant identity, check present-day retention, or grant access to evidence. A trusted host must re-resolve tenant authorization and retention before any later private read. `customer_supplied` claims fail closed. The adapter has no storage, network, provider, budget, answer, receipt, or promotion behavior.

The returned maintained plan stays `candidateOnly`, readiness `blocked`, execution `not_dispatched`, promotion `unpromoted`, and DecisionPort `unavailable`, even when the identity question is eligible for review. Its preparation status may be `prepared` when the existing preparation API finds eligible input; that does not change any readiness, dispatch, acceptance, or authority status. No completion observation or dependent support/conflict plan is created.

## Contract and acceptance boundary

The visible-status refusal contributes a local safety regression for issue [#11](https://github.com/Jevelopers-neatHack-2026/event-intelligence/issues/11) AC4: actual extraction and composition preserve the notice and its byte range, and the adapter refuses to create a lossy question. It does not implement occurrence assignment, accepted relevance or canonical source/fact mappings, or downstream consumer acceptance. Issue #11 remains open for those scoped outcomes and its predecessors.

This change supplies offline preparation evidence for the critical-evidence preservation part of EI-06 / issue [#16](https://github.com/Jevelopers-neatHack-2026/event-intelligence/issues/16) AC1 and pair-fact preservation part of EI-07 / issue [#17](https://github.com/Jevelopers-neatHack-2026/event-intelligence/issues/17) AC1. For #16 the unchanged mapped IDs are AGT-01, AGT-04, FIN-01, FIN-03, FIN-04, and EVAL-02; for #17 they are AGT-01, AGT-04, FIN-01, and EVAL-02. Their existing Agent and research, Finance and reliability, evaluation, and global ownership remains unchanged. This is a local candidate-preservation contribution only: it passes no full acceptance criterion, closes no mapped ID, changes no acceptance mapping, and does not complete either issue. Both leaves remain open; all required leaves #3–22, epic #1, and release #22 remain open.

The maintained preparation limits bound the plan, while this adapter also caps its serialized immutable sidecar at 65,536 UTF-8 bytes. It counts JSON bytes over the sanitized projection before hashing or full serialization, fails the whole preparation at the first observation or sidecar over-cap, and never truncates critical evidence. The language metadata map is capped at eight evidence IDs before descriptor copying; observation creation stops at 32 before constructing the first over-cap observation, though the current eight-source/two-candidate projection reaches at most 16. Decision references have a separate 1,024-entry bound derived from the selected-pair claim and per-claim support limits. These caps bound this local preparation work and do not establish trust, current retention, or private-read authorization.

Still outstanding under #16/#17 are canonical source-to-target protocol acceptance, trusted transport and tenant/retention checks, JEV/public response validation, actual answer and provider-receipt binding, attempt-level usage and billing evidence, owner approval, source-authority decisions, and the release gate. Finance, trusted-app, Creative, and release work remains open under its existing owners.

The producer/consumer contract still needs an owner-reviewed handoff under EI-X01 / issue [#3](https://github.com/Jevelopers-neatHack-2026/event-intelligence/issues/3). That producer must accept the canonical colon-versioned ID `Q-EI-IDENTITY:v1`, preserve the exact registry version/hash and question definition hash, and bind the selected pair to the target-binding, target-state, and question-instance hashes emitted by the maintained preparer. A result and its provider receipt must bind back to those same values; no identity answer may unlock dependent questions without a separately accepted identity-stage result and required review. The owner must define the canonical result and receipt schema, its attempt linkage and validation, and transport/privacy/retention revalidation before any private access. The current candidate contract’s restricted alias-key grammar and missing EI target hashes do not authorize alias mapping. This is a proposed handoff requirement, not an accepted contract. This adapter creates no DecisionPort request, result, receipt, or transport metadata, and its sidecar is not a JEV input.
